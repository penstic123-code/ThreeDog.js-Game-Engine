# Commands and debugging details

The scripts in `package.json` forward to the CLI `threedog` (from `@threedog/tools`; the root `build` runs each workspace's own `build`);
**`threedog xxx` on this page means `node node_modules/@threedog/tools/bin/threedog.mjs xxx`** (in this repo: `node packages/tools/bin/threedog.mjs xxx`): plain node starts fastest. `npm run xxx` runs the same command (npx adds about 2.5 s per call, so it is not used here). The tools find every path through their `paths.mjs`, in the engine repository and in a game
installed from npm alike. Every command checks its options: an unknown or misspelled one fails and lists the valid ones (dev bridge commands read their own options; `dev` / `build` / `preview` pass theirs to vite).

## Running one game only
After `-w` write the directory or the package name (inside a game directory a plain `npm run ...` does the same):
- Dev: `npm run dev -w games/my-game`, or from the root `npm run dev -- my-game` (part of the name is enough); no name means the engine example. To
  change the port (default 5173; if taken it moves to the next one): `npm run dev -- my-game --port 5000` (the game name must come first, the
  remaining arguments go to vite untouched; don't add another `--`).
- Test: `npm test -w games/my-game`, or `npm test -- -w my-game`; `npm test` at the root tests every workspace (engine + each game).
- Build: `npm run build -w games/my-game`; `npm run build` at the root builds all (every *.html in a workspace root is bundled, no change to
  vite.config.js needed).
- Screenshot / bake / compress models: `npm run shot -- -w my-game / --describe-only` (`--out day.png` your own name, still in `.threedog/shots/` (a path with a directory is written as given), `--tier low|high` render at that device tier (default: the desktop tier, skipped effects are named), `--keep` timestamped file name, look numbers and hints after every shot, `--no-look` skips them, `--ref image` also compares with a reference, `--json` one JSON object; an unknown option fails naming the closest one), `npm run bake -- -w my-game`, `npm run assets -- -w my-game`.
- A game's tests: every `games/<game>/tests/specs/*.mjs` runs (each exports a `specs` array; the runner finds the files, nothing to register); without
  `tests/specs/` a smoke test runs automatically (page opens, engine ready, no console errors). Minimal example:
```js
// games/my-farm/tests/specs/farm.mjs — export a specs array, one entry per page
export const specs = [{
  name: 'farm: pick up apple',   // npm test -- apple matches by name substring, any case
  url: '/?cutscene=skip',        // page path + URL parameters
  async run({ page, check, ev, frames, wait }) {
    // ev(fn, arg): runs in the page (engine is available). The function is serialized, so it can't use outer variables; pass them as the argument:
    const n = await ev(id => engine.inventory.count(id), 'apple');
    check('no apple at start', n === 0, `actual ${n}`);   // check(label, passed, details on failure)
    await page.keyboard.press('KeyE');                   // page is a Playwright page: keys, clicks
    await frames(3);                                      // wait 3 frames of the real-time loop (software rendering is slow; waiting by frames is more reliable than wait(ms))
    check('has apple after pickup', await ev(id => engine.inventory.count(id), 'apple') > 0);
  },
}];
```
  Tests run against the built bundle (not the dev server): main.js must set `window.engine = engine;` before `await engine.start()`, otherwise the
  test waits for the engine until timeout (the error explains why).
- New game: `npm run new-game -- name [--open-world] [--example]` (blank scene with a camera by default; `--open-world` adds generated ground, sky, follow camera and a player; `--example` adds a sample on top; see `recipes/01-new-game.md`).
- Game in your own folder (outside this repo): after `npm install threedog three@~0.187.0 @threedog/tools`, run `node node_modules/@threedog/tools/bin/threedog.mjs init [folder] [--open-world] [--example]` (folder: the one to create, default the current folder): it copies the new-game template without overwriting anything, merges package.json and writes `.mcp.json`, so Claude Code opened in that folder starts the threedog MCP server by itself.

> Git Bash (MSYS) rewrites arguments that start with `/` into a path under the Git install (`/` turns into `C:/Program Files/Git/`). Page arguments (`shot`, `capture`, `--page`) undo that by themselves; if the Git folder cannot be found the error says so: then write `shot styletest`, set `MSYS_NO_PATHCONV=1`, or use PowerShell.

> Windows PowerShell 5.1: `Get-Content` / `Set-Content` without `-Encoding utf8` read and write UTF-8 files in the system code page (mojibake, lost newlines). Pass `-Encoding utf8`, or edit files with your editor tools.

## Command table
| Command | When to use |
|---|---|
| `npm run dev` | Development. Browser errors are sent automatically to the terminal and to the workspace's `.threedog/errors.log` (e.g. `games/my-game/.threedog/errors.log`): read that file first when something breaks, before taking screenshots. Known error classes carry `Possible cause: …` and `Read: recipes/…` lines (tables `core/errorCodes.js` for engine errors, `core/errorHints.js` for browser / JavaScript ones) |
| `npm run check` | Run after every change (order: if the docs need regenerating `map` -> `check` -> related tests; otherwise `check` -> related tests): rule checks (`packages/tools/rules/`, the engine's hard rules among them; detection and allowlists are at the top of each file; the save round trip is in npm test) + types + content validation + generated docs up to date. Errors print in full, warnings as one count line per rule; `-- --verbose` lists them (the first 15 per rule), `-- --all` every one. `-- --rule R4` runs one rule (`R04` works; an unknown id fails and lists them), `-- -w game` (or `threedog check -w game`, or `check` run inside a game folder, as `new-game` does) reports only that game's rule, type and content problems and sets the exit code from them alone, with other games and the engine as one count line each; plain `check` at the repo root stays repo-wide (run it before committing engine changes) |
| R40 bypass hints (part of `check`, warnings only) | Game code that hand-rolls timers, `Math.random`, an inventory or grid/height blending, or hand-colors a material in a file that also takes style materials (`makeMaterial`), is pointed to the engine system that already does it. Hand-made materials elsewhere, and anything in art code (`style/`, `art/`, `assets.js`, `art.js`), are the plain three.js route and not hinted. Off per line `// hint-off(kind)`, per file `// hint-off-file(kind)`, per project `package.json "threedog": { "hints": false | { "kind": false } }`, per run `THREEDOG_HINTS=off`. ## Reproducing a scenario and debugging
- Add `?time=18:30&weather=rain&pos=40,-20&save=slot1&cutscene=skip&state=name` to the URL (effective in development).
- In the console / tests: `engine.describeText()` reads the state as English text; `engine.step(seconds)` fast-forwards synchronously (no rendering);
  `engine.pause()` stops the real-time loop.
- To wait for the page: `page.waitForFunction(() => window.engine?.stateApplied)` (start has finished and all URL parameters are applied); never read
  `_`-prefixed private fields. When the dev bridge / `npm test` / `npm run shot` cannot reach the engine (no `window.engine` after 40 seconds, or it
  exists but never becomes ready), the error states the page status, the latest page errors and the fix.
- Advancing dialogue headlessly: `engine.step(1)` lets the typing finish, then press a number key or run
  `engine.ops.run('dialogue.choose', { index: i })` (while typing it completes the sentence first).
- Debug objects on window: `window.engine = engine` is already declared; for a game's own, write `/** @type {any} */ (window).game = {...}`
  (`npm run types` reports properties on window as web hints, not errors).
- To operate a running game use the dev bridge, see `recipes/16-dev-bridge.md`.

## Folder guide (inside packages/engine)
- `core/` core: Engine (main loop, ground, step/describe), Events Input Saves Assets Audio I18n Clock Vars Jobs Stream Rays Budget UrlState Animator.
- `modules/` modules, one folder each, installed with `engine.use`; list in `CODEMAP.md`.
- `render/ ui/` material factory, post-processing; UI basics (windows, UI focus stack, toast, fadeScreen, worldToScreen).
- `index.js index.d.ts types/` entry and API declarations (`types/generated/` is generated from source JSDoc, never edited by hand).
- `examples/world/style/` is the world example's own small look (starting values and material roles), not a recommended one; `examples/world/art/`
  is its art: `index.js` exports the asset pack `assets`, `models.js` the procedural trees / rocks, `humanoid.js` the humanoid body asset, `shapes.js` the pickup shape.
  The bloom / outline / ao effects are in `packages/post-effects/` (`@threedog/post-effects`). The terrain preset `terrainPreset()` is a separate package, `packages/terrain-noise/` (`@threedog/terrain-noise`).
- `examples/world/` is the engine example (open world `/`, content-only placement). The small city (level, no terrain, no style, top-down) and
  the co-op page are test pages in the engine repository (`tests/city/`, `tests/coop/`), opened at `/tests/city/index.html` and `/tests/coop/index.html`.
- `tests/` specs/*.mjs test items (found by the runner), `<name>/index.html` test pages, fixtures/ test assets. `public/` art for the examples.
- Each game `games/<game>/`: package.json, vite.config.js (one line, gameConfig), index.html, main.js, `content/` (items npcs dialogues quests pickups
  containers props templates triggers actions places level vegetation audio grids renames rules, plus the game's own kinds registered in
  `content/rules.js`; only these file names are read), `public/` (art; Blender source files go in `art/models/`), DESIGN.md, GAMEMAP.md (generated), CLAUDE.md.
- Each workspace has its own `.threedog/` (browser error log errors.log, screenshots shots/, generated cache) and `dist/`; neither is committed.
