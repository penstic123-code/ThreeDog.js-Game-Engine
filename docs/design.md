## 1. 一句话

**引擎是一块带很多插槽的底板。AI 用 three.js 写代码，引擎自动或半自动地把它接进来，和引擎原有的东西一起工作，而不是去取代引擎。**

three.js 是画笔，引擎让很多支画笔同时在一张画上画而不互相涂掉，并且出了问题能查出是哪一支画的。

## 2. 为谁做

- **主要使用者是 AI 编程助手**，用户本人不写代码。所以"AI 第一次看就能用对"是最高优先级之一。
- 目标是**中大型网页 3D 游戏**，不限玩法和美术风格：慢生活、动作、射击、生存沙盒、横版，都要能做。
- 三件事都要：**做得快、效果好、AI 特别擅长**。要取舍时先问用户。

## 3. 原则（不能违反）

| # | 原则 | 具体意思 | 现状 |
|---|---|---|---|

## 4. 结构：底板、插槽、插件

### 4.1 底板分四层

| 层 | 内容 | 能不能不要 | 现状 |
|---|---|---|---|
| 核心 | 主循环和**单一时间来源**、事件、按键、存档、**生命周期**、**共享点和插槽**、状态查询（describe）和报错、两种渲染方式的启动、资源加载 | 不能，这就是底板 | 🟡 大体统一过 ✅；"谁说了算"的四套机制见 P8 |
| 工程模块 | 天空天气昼夜的信号、地形数据和分块加载、物理、寻路、角色和控制、相机、声音、界面焦点、联机 | 按需安装，外观部分都能换 | 🟡 地形、植被、天气已拆成"数据 + 外观" ✅，地形的数据部分不再读任何外观设定（颜色在地形的材质里，雾由游戏写）✅；水的数据（水位、水体）在核心、外观在模块 ✅，但网格不能换（见 P3）🤝；粒子是一个外观模块，有契约 ✅。声音和角色动画还没有"换成自己的"插槽（见第 14 节） |
| 玩法功能 | 背包、任务、对话、触发区、交互、过场 | 都是功能位，可以换成自己写的 | 🟡 `provides` / `replaces` / `requires` 都能用，背包契约已补全，引擎对可替换模块的调用必须在契约里（规则 R50）✅。还差：内容加载器写死了 15 个模块和它们的数据格式，自己写的模块没法登记"我认内容里的哪一段"，换掉任务、对话后内容照旧按引擎版的格式喂进去（大，和编辑器一起做）；背包、任务自带窗口和开关键，可以用 `engine.ui.set('inventory', false)` 关掉换自己的界面（菜谱 03）🤝 |
| 不归引擎 | 具体的美术、成品外观、游戏规则 | 归 AI 和游戏，可以放进个人素材库复用；画面是游戏自己的 `picture/` 代码（普通 three.js），起步代码由 `new-game` 生成、归游戏；不同做法放素材库，没有内置画风包 | ✅ 素材库 `threedog lib` 已做，读不了的条目会列出来 |

### 4.2 插槽分两种

- **能插很多个的**（绝大多数）：场景里的物体和灯、材质插槽、后期链、公共画面值、玩法里的公共数值、事件、按键动作。AI 写的东西往上插，和引擎原有的东西共存。
- **只能有一个的**（少数）：天空、地面外观、植被外观、色调映射、相机、各个功能位（背包等）。AI 要用自己的版本时，用 `replaces` 替换掉引擎原来的那个。
- 整块替换按大小只有一种写法：只换大件画出来的**那一个东西**（天空穹顶、地形或植被或水的材质、一种粒子），直接设或交一个自己的 three.js 对象（例如 `engine.sky.replace(...)`、`engine.terrain.material`）；连行为、存档一起换**整个模块**，用 `engine.use(mine(), { replaces })`。`replace` 不收模块，`replaces` 不收 three.js 东西。✅（植被外观是整个模块，所以用 `replaces`，不算第二套写法）

### 4.3 接入分三档，越自动越好

1. **自动**：引擎能从代码里看出来的，AI 不用多写一行。例如往场景加物体、加灯、改雾、改背景。✅ 改雾、改灯、改背景会让出；加物体、加灯自动接上；插件文件夹里的文件开局自动插上（一个 Pass 放进 `plugins/` 也是）
2. **半自动**：引擎看不出意图的，AI 写一行声明。例如"我在雾浓度上乘 1.4"（`mul`），"这是一个画面类模块"（`type`），"把这个 Pass 加进后期链"（`engine.post.add(pass)`）。✅
3. **替换**：只用在只能有一个的插槽。✅（自己写的天空物体引擎认不出，要用 `engine.sky.replace`，见 P1 🤝）

### 4.4 插件长什么样

- 简单的东西就是**原生 three.js 对象**，不需要包任何外壳：一个物体、一个材质、一个后期 Pass。
- 复杂的东西写成**模块**：声明类型（`type`）、提供什么（`provides`）、需要什么（`requires`），引擎帮它接好生命周期、存档、按键、冲突检查。
- **插件文件夹**：游戏的 `plugins/` 文件夹，放进去的文件开局时按导出的东西自动接上；`lib pull` 把代码拉到这里。✅ 导出一个函数时两种渲染方式下报同一个看得懂的错；`lib pull` 把代码放进 `plugins/<名字>/`，再写好接入文件 `plugins/<名字>.js`
- **插槽表**：`describe().slots` 列出每个插槽插了什么、来自哪个文件、影响了哪些值。✅（也列出引擎自带的模块，读起来有点吵，可以接受）
- 拔掉一个插件，它造成的所有影响自动撤回，不留残渣。✅ 读档之后旧句柄也能撤（守卫测试 `tests/specs/shared-points.mjs`）

## 5. 冲突怎么解决（谁说了算）

- **引擎永远不悄悄替你挑。** 要么有固定规则自动解决，要么开发时报错，让游戏用一行代码决定。✅
- **公共值按层合成**。AI 只需要记三个概念：**基础值**（游戏设定）→ **效果在上面乘**（过场、技能）→ **玩家设置封顶**（只能限制，不能强开）。完整的层是：引擎默认 < 游戏 < 效果 < 系统 < 设置 < 调试。✅
  - 设置层只能往下调或关掉：数值只接受 `clamp: { max }` 和 0 到 1 的 `mul`，开关只接受 `set: false`；往上调的写法开发时直接报错，并说该写在游戏层。游戏自己的设置行也用同一条公开写法（`settings.define({ limits })`）。✅（守卫测试 "shared points: ... settings restrict only"）
  - **设置排在系统之上，只能限制**：玩家的限制对系统层（过场、菜单、拍照工具）也有效，玩家关掉的画面抖动、闪光，过场不能再打开。只有调试层能盖过玩家的设置。（2026-11-03 主人定下）✅
- 合作就用 `mul` / `add`，自己说了算就用 `set`。同一层里两个**不同**主人都 `set` 同一个值时，开发时报错，并给出三种可以照抄的改法。✅
- 只有几方真的会一起改的值才是公共值：信号（`engine.mod` 合成）、阴影、后期参数、时间流速。灯、雾、曝光只有一个写的人，不是公共值（第 7 节）。AI 自己的物体、材质、贴图不需要登记。✅
- **游戏自己的几段画面代码之间也要配合。** 灯、雾这些值不是公共值，所以共享点管不到"同一个游戏里两个文件写同一盏灯"。这些代码对引擎来说都是"游戏"一方，引擎不替它们排先后；规矩是按值的种类分（第 7 节"画面代码之间的配合"）：只能有一个的值用 `provides` 占位，第二个占位的件安装时报 `shared-taken`；多方要改的值由游戏定义成共享点（`engine.stacks.define` + `engine.mod`），一处读结果写 three.js；只是加东西不算冲突。没声明的写入靠开发工具抓：同一帧两处写同一个值，报出两个 `文件:行`。🟡 见第 7 节
- 游戏第一次设的值被效果改动时，开发时提示一次（例如"你设了 3，下雨时显示 1.8"）。✅
- **角色控制**：每个角色同一时刻只有一个控制者，分四层：平时 < 脚本 < 过场 < 联机。上层接管时下层是暂停，不是取消，结束后自动还回去。✅（机制和共享点分开 🤝，见 P8）
- **按键**：按场合分层；模块只声明需要哪些动作，由游戏绑键；默认只有一套基础键。✅
- **时间**：只有一个计数器，其余全部是它推算出来的视图；子弹时间、加速、暂停用乘法叠加。✅ 绕开共享点的 `time.manual` 已删

## 6. 模块类型

一共 7 种，没有子类型：`world`（数据，不画东西）、`picture`（显示）、`actor`（角色）、`rules`（玩法规则）、`ui`（界面）、`net`（联机）、`tool`（一次性工具）。同一类型里的差别靠声明来表达：写了哪些公共值、占了哪个插槽、往哪个材质插槽加了代码、支持哪种渲染方式。✅ `type` 是唯一的分类：外观、界面模块出错只停掉自己，游戏不卡死。

- 越界开发时报错。🟡 开局时查四条（显示类模块不能定义操作、显示和界面模块不能写世界记录、界面模块不能绑键、界面模块不能登记存档，`core/engine/moduleTypes.js`），数据模块画东西由规则 R47 静态检查 ✅；`actor`、`net`、`tool` 三种还没有任何检查，显示类模块登记存档、工具做完不撤回也不拦（小到中，要接着做）
- 模块之间只能用公开接口和事件，不许伸手进别的模块内部；核心不写死具体模块的名字。✅ 规则 R16、R46 检查（也认绕路的路径和动态 `import()`）；核心里只剩 3 处点名模块（content、calendar、flow），每处都在规则 R27 里写了理由 🤝

## 7. 引擎提供什么，AI 写什么

**引擎提供**：three.js 没有、大多数游戏都要、自己写容易出错、而且要和别的系统配合的东西。例如画面的信号（时刻、太阳方向、天气的量，由很多系统合成好给游戏读）和工程（大场景分级阴影、阴影更新预算、灯的数量管理、烘焙光照探针）、存档、时间、大世界分块加载、物理、寻路、两种渲染方式下画面一致，以及让 AI 能查问题的状态查询、报错和检查。

**AI 写画面代码**：灯、雾、曝光、色调、环境贴图、自己的材质，都是游戏 `picture/` 文件夹里的原生 three.js，引擎不再包一层。
**AI 用引擎大件给出的材质**：地形、植被、水、天空穹顶、雨雪是引擎的工程，它们给出 three.js 材质或信号，游戏直接设；要整块换，就交一个自己的材质。
**AI 用引擎的能力**：three.js 没有的工程，收 three.js 对象、返回句柄（阴影跟随和分级、后期融合、把天空渲成环境贴图）。
**AI 自己写**：引擎没有的，或者要独特风格的（模型、贴图、shader、体积雾、手绘风、自己的天空和水）。

注意：有些东西引擎只给**信号**，效果要游戏自己做。例如下雨时地面湿润，引擎只提供"现在雨下得多大"。

**信号进，画面出**（2026-11-04 主人定下，详见 `docs/plans/2026-11-04-visuals-signals-in.md` 第 4 节）✅：
1. **每个 three.js 外观值只有一个写的人：游戏的画面代码。** 引擎不在背后改灯、雾、色调映射、曝光、背景、游戏的材质。这句话管的是引擎和游戏之间：一个游戏的几个画面文件、从素材库拉来的条目，对引擎都算"游戏"这一方；它们之间谁写什么，按下面"画面代码之间的配合"办。引擎大件的内部（地形分块的网格、植被的实例矩阵）是工程，照旧由引擎管。天空只算信号、画穹顶，不写灯、雾、曝光、环境贴图；没写画面代码时是静止的中性占位灯（守卫测试 `tests/specs/sky-writes-nothing.mjs`）。
2. **冲突在信号层解决。** 天气、过场、子弹时间、玩家设置要影响画面，就改信号（共享点照旧用 `engine.mod(...)` 合成），画面代码读合成后的值。画面层不再有"层"。
3. **信号是普通的值，读法只有一种。** 太阳方向、白天程度、时刻、天顶色和地平线色、雨雪雾的量、地面湿度、风、季节色调都放在 `engine.uniforms`：着色器里直接共享这个对象，JS 里读 `.value`。
4. **引擎的大件开放外观。** 它们给出 three.js 材质或统一值，没有"材质角色表"这一层转手。
5. **起步代码是游戏自己的。** `new-game` 生成几十行起始画面文件（中性灰），游戏可以改，也可以删掉重写。不同风格的现成做法放在素材库，复制进游戏后归游戏所有。
6. **检查留在引擎，不能骗人。** 截图检查、诊断视图、全黑和雾的判断都在引擎。工具自己不确定时要说不确定或直接报错；量得到但可能误报的，写明"可能是什么"，不算结论。`describe().picture` 直接从 three.js 读当前的值（色调、曝光、雾、环境贴图、背景、每一盏灯、阴影），所以它和屏幕上的画面不会对不上（守卫测试 `tests/specs/describe-render.mjs`）。诊断时用 `engine.debug.override(owner, 对象, 属性, 值)` 临时改任何一个 three.js 值，改的只是屏幕。
7. **单个物体的状态走 `picture/` 的具名接口。** 打灭一盏路灯、一块招牌闪烁不是全局信号。玩法代码不直接改灯和材质，只调 `picture/` 对外给的名字，名字由游戏自己定，引擎不提供这一层。
8. **`picture/` 的着色器写法跟着渲染方式走。** 新游戏默认 WebGPU，画面用 TSL 写；`--webgl` 的游戏用 `ShaderMaterial`、`onBeforeCompile`。两种写法不能混用，用错时引擎点名报错。引擎自己的补丁两种都写。
9. **画面代码必须读画质档位。** 引擎拦不住它无视档位，所以 `picture/` 读 `engine.tier`，再由检查量出超标。
10. **能力都是 three.js 的形状。** 收 three.js 对象，返回句柄；只处理游戏交给它的对象，不在背后改值。

分层（用来判断一件事归谁）：

| 层 | 负责 | 不做 |
|---|---|---|
| 内核 | 循环、时间通道、世界记录和存档、输入、事件 | 不碰任何渲染值 |
| 信号 | 时刻、太阳方向、天气、湿度、风、画质档位 | 不写灯、雾、曝光。对画面代码只读；玩法要影响画面，走规则 2 改信号 |
| 能力 | 地形分块、植被实例、级联阴影、灯池、后期融合 | 只处理游戏交给它的对象 |
| 检查 | 截图、诊断视图、性能预算、指路提示 | 不改画面 |
| 游戏 `picture/` | 灯、材质、雾、天空颜色、调色，都用原生 three.js | 玩法代码不直接改灯 |

**第二种画面语言已删除**（2026-11-04 主人批准）：原来的外观接口是 18 个部件、每个六个动词，和 three.js 写的是同一批值。规矩是能力留下、第二种语言删掉；每个部件的去向写在计划的 C1 对照表里。部件和框架都已删完 ✅。

### 画面代码之间的配合

外观层删掉后，"一个值一个写的人"只是一句规定，没有东西执行。AI 写的几个文件、不同来源的 three.js 代码放进同一个游戏，可能两处写同一盏灯、自写着色器没接雾和色调、透明物体排序打架、灯数变化引起重新编译。引擎不包装 three.js，只用现成的模块机制和开发工具（详见主计划同名一节）。

**值分三类，规矩不同：**

| 类 | 例子 | 规矩 | 冲突时 | 现状 |
|---|---|---|---|---|
| 只能有一个 | 天空、雾、色调和曝光、环境图、主光 | `provides` 占位 | 第二个占位的安装时报错（`shared-taken`），`replaces` 换掉 | ✅ 机制（守卫测试 `tests/specs/shared-points.mjs`）；名字约定表 `core/scene/pictureSlots.js`：`sky`、`fog`、`tone`、`environment`、`background`、`sun`（守卫测试"picture parts"） |
| 多方要改 | 过场和日落都压暗太阳 | `engine.stacks.define` + `engine.mod`，一处读结果写 three.js | 叠乘有固定算法；两方 `set` 报错 | ✅ 菜谱 62 写了（守卫测试 `tests/specs/shared-point-layers.mjs`） |
| 只是加东西 | 又一盏灯、又一个物体 | 直接加 | 不冲突，只算预算（灯数、阴影、绘制数） | ✅ |

**画面件：要和别人共处的画面代码写成一个模块。** `type: 'picture'`，用 `requires` / `provides` 声明，`install(e, ctx)` 里面是普通 three.js，读信号，用 `ctx.track` 登记卸载时要撤的东西。单人写的小游戏不用这样写，普通函数照旧；只有要和别的来源共处、或要进素材库时才用。这是从代码推出来的方案，三个不同来源的画面件放进一个游戏的配合测试还没做 ❌，所以这条路没有被真实题目验证过。

**没声明的写入由开发工具兜底：** `core/inspect/pictureWriters.js` 记录灯、雾、曝光等值是哪一行写的（`describe('picture')`、`explain({ picture })` 能查），同一帧两处写同一个值时报 `picture-conflict` 和两个 `文件:行`（守卫测试"picture writers"）✅。它只报不拦，只在开发服务器里工作，每帧都写的值是抽样看的，同一文件里两个匿名函数算一处会漏报。截图检查量出自写 `ShaderMaterial` 没接雾或色调、灯数在运行中变化、透明物体绘制顺序问题 ✅（`tests/specs/look-own-draws.mjs`，改名后以新文件名为准）。

**写了别人占位的值：** 工具知道谁占了位，别人写了就报 `picture-held`，点名占位的件、写的人和两个 `文件:行`；`describe('picture').picture.writers.values` 里分得出 `holder` 和 `stray` ✅。**卸载残留：** `engine.unuse(name)` 或 `replaces` 卸掉画面件后，还留着的灯、物体、后期效果、帧回调、雾和背景报 `picture-leftover`，点名这个件 ✅。两项都只在开发服务器里，守卫测试"picture parts"。

**还没有的：** 后期顺序的检查 ❌；引擎统一管共用的显卡缓冲（法线、速度）❌，见 `docs/plans/2026-11-04-light-and-volume.md`。

### 资产要能配到一起

单件好用不等于放在一起好用。尺寸、朝向和原点、画风、颜色空间、骨骼、代码接口、同一个值两个写的人，都可能配不上（对策表在 `docs/plans/2026-11-04-asset-reuse.md` 第 2b 节）。定下来的原则：

- **所有画面条目一种形状，就是上面的画面件。** 这取代了资产计划 2b 里"收 `THREE` 和参数、返回对象和 `update(signals)`"的写法，也取代主计划 6.2 的写法。AI 拉来海面和天空，不用猜怎么连：都是模块，都读同一批信号，`picture/index.js` 只是接线。
- **条目写明自己的事：** 需要、提供、会写哪些 three.js 值、尺寸、风格、一段十行用法。缺依赖报错并给出安装写法。
- **条目不写死颜色**，材质由游戏的 `picture/materials.js` 统一给，画风才统一得起来。
- **约定 1 单位 = 1 米。**

现状 ✅：`entry.json` 带这张卡片（需要、提供、会写的值、尺寸、风格、用法，`lib add` 时量出），`lib check` 查缺依赖和两个写入者。

**后期效果只有一个入口**：`engine.post.add(...)`，收 three.js 的 Pass、WebGPU 的节点函数或带开关的效果，返回句柄；游戏代码、插件文件夹都走它，开关统一用句柄 `handle.enabled = false`。`engine.post.own()` 把整条链交给游戏。✅（2026-11-03 主人定下，守卫测试 `tests/specs/one-post-entry.mjs`）

## 8. 两种渲染方式（WebGL / WebGPU）

- 开局时选，运行中不能切换（three.js 本身也是这样）。WebGPU 不可用时按设置退回，退回时不会崩。✅
- **选哪个是做游戏第一天的决定，因为它决定画面代码用什么语言写。** `new-game`、`init` 默认 WebGPU 加 TSL（`main.js` 先引入 `threedog/tsl`，再 `createEngine({ renderer: 'webgpu' })`）；`--webgl` 选 GLSL。`createEngine` 自己不带 `renderer` 时仍是 WebGL。半路换就是重写自写的着色器；普通 three.js 材质和灯两边都能用。浏览器没有 WebGPU 时游戏退到 three 的 WebGL2 后端继续跑，`describe().renderer` 写明原因。✅
- WebGPU 设备丢失时走和 WebGL 上下文丢失同一条路：暂停、发事件、提示刷新页面 ✅（`core/engine/page.js`；没有在真的设备丢失上跑过）
- **引擎自己的着色器补丁都写两份**：WebGL 一份 GLSL，WebGPU 一份节点版（TSL），两份做同一件事。规则 R49 检查引擎的补丁都有 WebGPU 版，缺了不让合并。例外是少数只有 TSL 版的后期效果（`@threedog/post-effects/tsl` 里的 `voxelGI`、`temporalAA`、`sunShafts`、`lightVolumes`），WebGL 上不可用：选了 WebGL 的游戏加它们会点名报错，退回到 WebGLRenderer 的设备上暂停。✅（2026-11-03 主人定下）
- 引擎自带的内容在两边画面一致，用逐像素对比来证明。🟡 地形、植被、水、天空、粒子、泛光 ✅；调色和色调阶段逐像素对比 ✅；描边、景深只比画面平均亮度（相差 3% 以内），环境光遮蔽只确认 WebGPU 上画出来了，两边算法本来不同（WebGL 另画一遍法线，WebGPU 从深度重建）（`tests/specs/post-webgpu.mjs`）——平均亮度证明不了是同一张画面，描边和遮蔽应该补分区域对比（中）；四个材质插槽（灯光声明、光照模型、雾声明、雾）只能用于 WebGL 🤝（WebGPU 的节点材质里没有对应位置，用了会点名报错）；半透明加雾两边一致 ✅；sRGB 图片当背景、开着色调映射时，两种渲染方式、开不开后期都一样 ✅（和普通 three.js 的 WebGL 不同：那边背景不做色调映射，见菜谱 56）；真显卡上跑过性能实测 ✅（2026-11-03，画面对比仍在软件渲染上做）
- AI 的效果只写了一种渲染方式时，开局点名报错。✅

## 9. 数据和代码

- **代码决定"怎么做"，数据决定"有什么、在哪里、是多少"。**
- 设计数据（内容、模板、摆放）放在游戏的文件里，有固定 id，可以用命令写回文件（`threedog content set`、`threedog tune`）。✅
- 运行中的变化存进存档；存档只存和初始内容相比的变化。✅
- 通过 `engine.ops` 定义的玩家操作会进操作记录，可以用于存档、联机、回放、撤销。🟡 直接改世界记录也会进存档，但不会进操作记录 🤝（理由见第 12 节）
- 浏览器里的编辑器（`docs/plans/2026-11-05-editor.md`）：点选、拖动、写回文件 ✅（只在开发服务器）；属性面板、新增、撤销排在 0.9 后面几刀。❌

### 资产复用（`docs/plans/2026-11-04-asset-reuse.md`）

- **素材库在引擎外面，拉取是复制，拉进来就归游戏**，可以随便改。不进模板、不默认启用。`threedog lib add / list / pull / page` ✅
- **已有：** 拉取留记录（`.threedog-lib.json`：来自哪条、改过没有，`lib status` 看）；玩法系统成为完整单位（种类 `system`，代码、内容、文字、测试、依赖一起走）；条目能证明自己能用（在空游戏里拉一次、跑一次）；`lib check`。✅
- **要补的：** 一个能筛选的素材库面板；让 `threedog how` 也搜素材库；组合配方（"海边黄昏"这样几件接好的一组）。❌
- **有意不做：** 自动更新游戏里的文件（拉进来就归游戏，这是不让游戏长得一样的前提）；依赖版本求解（只查缺不缺，不做包管理器）；在线市场和账号；把成品放进引擎。

### 场景结构（0.8 的决定，`docs/plans/2026-11-05-flat-content.md`）

- 对照 Godot 节点、Unity 组件和预制件看过：模板加摆放够当预制件，模板字段加模块接口够当组件，three.js 场景树够当节点树。
- **内容文件只放平铺的条目，运行时什么都不嵌套。** `template` 就是原型，`id` 就是实例。一组东西靠同一个地点放在一起：地点可以带 `rot`，条目的偏移和朝向跟着地点转，改一处地点整组跟着动（模型和碰撞一起）。`source` 是一个可查询的字符串，写明条目抄自哪个摆法。✅ 摆法文件 `content/arrangements/<名字>.js` 只有工具复制时读，运行时不读。
- 依据：九个真实游戏的 `content/props.js` 和 `templates.js` 都是空的，东西全写在代码里。先要的是平铺写法好用，不是更多层次。
- **有意不做：** 模板继承（JS 的展开写法 `{ ...chest, model: 'iron-chest' }` 就是变体，多一层规则更难懂）；组合预制件和部件覆盖；通用组件系统（AI 不用拖拽，一行模块调用更直接）；新的对象层和节点类型体系（和 P4 冲突）；`parent` 附着（箱子放在移动的船上由游戏在 `world.simulate` 里跟着写，手里拿剑用 three.js 的 `bone.add(sword)`）。什么证据能重开，写在上面的计划里。

## 10. 让 AI 看得见、查得出

- `describe()`：场景里有什么，每个值是谁写的、怎么合成出来的，谁在控制哪个角色，装了哪些模块、各是什么类型，引擎对 three.js 改了哪些地方（`threePatches`）。🟡 都查得到 ✅；但"谁说了算"分散在好几个表里（见 P8）
- 报错带规则和改法；开发守卫在 AI 写错时当场拦住。✅
- `threedog how` 按任务查文档；AI.md 是"任务 → 接口 → 教程"的索引，有大小上限。✅ 普通 three.js 写法和引擎写法分开标注
- 截图对比、资源浏览（也能画 WebGPU 的节点材质）、性能报告、调参面板、热更新。✅
- 工具报的要是真的：`describe`、`ops`、冒烟测试都不能说一个玩家按不到的动作"能用"。✅ 动作没键时写明，冒烟判失败
- 测试运行器不会假通过：没等待的检查、一个检查都没跑的测试项、什么都没匹配到的过滤都算失败。✅

## 11. 衡量

- **易用性 + 对比实测 + 画面实测**：一道难题《一天》，由新引擎和纯 three.js 各做一遍（`docs/testing/usability-tasks.md`）。引擎版本画面明显更差，或者 AI 被引擎挡住，都算引擎的问题。🟡 2026-11-04 用新模板和纯 three.js 在同一道限时题上各跑三次，盲评（`docs/testing/usability/2026-11-04-keeper-blind.md`）；《一天》两边还没比过；夜街那道试玩题要等 0.6 收尾时重跑一次
- 所有测试结果记在 `docs/testing/runs.md`。✅

## 12. 有意的妥协（复审可以质疑）

| 妥协 | 理由 |
|---|---|
| 引擎对 three.js 的改动一共十五处，全部列在 `describe().threePatches`（数字以代码里的 `notePatch` 为准）。整页范围四处：阴影材质、WebGPU 顶点、`Object3D.add/remove` 钩子、新增的 `ShaderChunk.threedog_*` 代码块。按物体或按渲染器十一处：进场景物体的 `material`、被打补丁材质的 `onBeforeCompile`（游戏自己的材质只有游戏调用 `applyEffects` 才打补丁）、引擎渲染器的 `render`、后期链第一个 pass 的 `render`、three 背景网格的 `onBeforeRender`、WebGPU 渲染器上的三个钩子（`fromMaterial`、`onNodeBuilderCreated`、`onDeviceLost`）、游戏灯在亮度为 0 时的 `shadow.autoUpdate`、HLOD 登记物体的 `visible`、开发服务器里记录画面值写入位置的存取器 | three.js 没有按物体挂钩的办法，自动接入要靠它们；每一处都写明管到哪、关掉后少了什么。十二处可以关掉；三处关不掉：`ShaderChunk` 代码块（引擎自己的补丁要用）、WebGPU 的 `fromMaterial`（打过补丁的材质要靠它）、HLOD（按登记解除，`remove()`） |
| 四个材质插槽只能用于 WebGL | WebGPU 的节点材质里没有对应位置；用了会点名报错 |
| 开着后期效果时，WebGL 每帧多花约 0.15 ms（画布自带的抗锯齿加上后期链） | 换来的是没开效果的游戏显卡时间省约四成（2026-11-03 协调者接受，`docs/testing/field/2026-11-03-perf.md`） |
| 水只能换材质，网格不能换 | 想整块自己画就不装水模块，水位和水体数据还在引擎里，游泳、浮力照样能读（菜谱 44） |
| 引擎大件自己的材质（地形、植被等）一直带着云影补丁，游戏自己的材质要自己调用 `applyEffects` 才加 | 大件的材质是引擎的工程，不是游戏写的值；游戏的材质引擎一律不碰，"游戏写了什么就编译什么"这条规则不受影响 |
| 游戏选了色调曲线后，纯色背景在直接渲染时画成一张 1×1 贴图 | 否则开关后期时背景颜色会跳；只在渲染时换，`scene.background` 不变，列在 `describe().render.defaults` |
| 天空还写两样东西：背景（backdrop / skybox）和阴影框跟随焦点 | 前者是穹顶的替身，后者是工程，不是外观；都登记在 `describe().owned`，直接写时引擎让出 |
| 自己写的天空物体引擎认不出来 | 看不出哪个物体是天空；`engine.sky.replace(sky)` 一行就接上（THREE.md） |
| 画面值归游戏后，引擎拦不住画面代码无视画质档位 | 不写值才是这条路的代价；拦不住就量：检查会报出超标，不替游戏改 |
| 画面代码的着色器写法只对应所选的渲染方式 | 用另一种方式的写法（WebGPU 上的 `ShaderMaterial`，WebGL 上的节点材质）会点名报错；引擎自己的补丁仍是两种都写 |
| 写入记录只报不拦，而且只在开发服务器里 | 要在发布版也拦，就得把 three.js 包一层，外观层就回来了；打包后的游戏 `describe` 写明没记录 |
| 角色控制、按键场合和共享点是分开的机制 | 它们是"上层暂停下层""遮住下面的"，不是合成出一个数；但查询应该统一（见 P8） |
| 背包、任务自带界面 | `engine.ui.set(名字, false)` 就能关掉换自己的，不卡人 |
| 核心里点名 3 个模块（content、calendar、flow） | 每处都有理由，写在规则 R27 里 |
| 选项表在代码和类型声明里各写一份 | 规则 R6 保证两份一致；以后能从同一张表生成类型最好 |
| 直接改世界记录不进操作记录 | NPC 这类每步都在动的东西，每步记一条操作太重 |
| 渲染方式只能在开局时选 | three.js 本身就是这样 |
| 拉取素材是复制，不是链接 | 每个游戏各改各的，防止所有游戏长得一样 |
