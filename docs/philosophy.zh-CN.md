# ThreeDog 的设计思路

[English](philosophy.md) · 中文 · [常见问题](faq.zh-CN.md) · [一路走来](evolution.zh-CN.md)

让 AI 编程助手做一个 three.js 游戏，它面对的是一个空场景。在碰到玩法之前，它要先写存档、时钟、碰撞和相机，到下一个游戏又写一遍，写法还略有不同。这些系统之间也得对得上：读档要恢复天气，过场要停住玩家，新加载的地块要进物理世界。ThreeDog 就是为这种配合而做的。three.js 是画笔，引擎让很多支画笔在同一张画上画而不互相涂掉，出了问题还能查出是哪一支画的。

引擎的主要使用者是 AI 助手，不是坐在键盘前的人，下面多数决定都由此而来。AI 本来就熟悉 three.js，很少细读文档，又相信工具告诉它的结果，所以引擎要贴近 three.js，索引要短，报告问题必须说实话。

> **现状。** 本文讲的是 0.9。0.6 是引擎不再替游戏画画的第一个版本。0.5 及以前的版本带着下一节说的外观层。最后一节列出已经计划、还没做的部分。

## 引擎为什么不再替游戏画画

到 0.5 为止，画面握在引擎手里。引擎有一张外观表，分 18 个部件，每个部件有同样的六个动词，游戏要改雾就写 `engine.look.fog.set({ far: 60 })`。这样看着整齐，用起来才发现两个代价。这些值 AI 本来就能用 three.js 写，现在却要多学一门语言。而且这张表定死了上限，表里没有的东西，得先等引擎开一个入口。

0.6 把关系倒了过来。游戏在自己的文件夹里用普通 three.js 写画面，引擎只交出信号：现在几点、太阳在哪、雨下得多大、玩家能看多远。

```js
// 游戏的画面代码。除了读信号，这里没有引擎自己的语言。
engine.onRender(() => {
  sun.intensity = palette.sunBright * engine.uniforms.uDaylight.value;
  scene.fog.far = palette.fogFar * (1 - 0.6 * engine.uniforms.uRain.value);
});
```

背后的规矩是每个 three.js 值只有一个写的人，就是游戏。引擎不再在背后改灯、雾、曝光和游戏的材质，于是“我改了值，它又变回去了”这类问题不会再出现。地形、植被、水、天空穹顶、雨雪这些大件仍是引擎的工程，但都会交出自己的 three.js 材质，游戏可以改，也可以整个换掉。

这样做有实实在在的代价。新游戏从灰色起步，画面要游戏自己写。起始文件和个人素材库能减轻这份工作，但不能替代它。

## 各部分的分工

| 部分 | 负责 | 不做 |
|---|---|---|
| 内核 | 主循环、时间、存档、输入、事件，以及和 three.js 的衔接（场景、渲染器、加载、阴影，以及列在 `describe().threePatches` 里的改动） | 不决定画面长什么样：灯、材质、雾和颜色归游戏 |
| 世界 | 世界记录（`modules/world`），是内核上面的模块 | 不管记录怎么画 |
| 信号 | 时刻、太阳方向、天气的量、湿度、风、画质档位 | 不写灯、雾、曝光 |
| 能力 | 地形分块、植被实例化、级联阴影、灯数预算、后期效果链 | 只处理游戏交给它的东西 |
| 检查 | 截图、诊断视图、性能预算、下一步指路 | 不改画面 |
| 游戏 | 灯、材质、雾、天空颜色、调色、模型、规则 | 不直接伸手改别的系统的状态 |

一件事该不该进引擎，看三个问题：three.js 没有它，多数游戏都要它，而且它自己写容易出错，或者必须和别的系统配合。跟着玩家走的阴影系统三条都符合。木头材质前两条就不符合，所以留给游戏。

## 互不相识的代码怎么共用一帧

帧的顺序、模块要求、一个公式算出的共享值、引擎给直接写入让路、已知的缺口和各条原则，都在 [design.md](design.md) 第 2 到第 5 节，只写在那里一处。

## WebGL 还是 WebGPU

游戏要在开工时选定渲染方式，因为两边的画面代码写法不同。新游戏默认走 WebGPU，用 three.js 的节点语言 TSL，一些实时效果只有走它才能做。加 `--webgl` 则用 GLSL 着色器，这是 AI 见得最多的写法。浏览器没有 WebGPU 时，游戏仍在 three 的 WebGL2 后端上跑。中途换就要重写画面代码。引擎自己的效果两种写法都有，仓库里有一条规则，拒绝只写了一边的补丁。

## 目前的证据

证据还很少。两个小游戏做过十次限时测试，一半用引擎，一半用纯 three.js，其中约三分之二的代码是画面代码。所以在这种规模的游戏上，引擎大概只能省下五分之一的工作。这些测试里没有出现引擎和游戏抢值的情况，这也是决定继续拆掉外观层的依据。在一次八张截图的盲看里，一位评审只认对了三张，可见引擎不会明显改变小游戏的样子。存档、分块加载和协调更重要的大一些的游戏，还没有测过。

## 接下来

- 素材库：记录拉取的东西来自哪里，写明它需要什么、会写哪些值，并检查几样东西能不能配在一起。
- 组合模板：摆放一个物体时，它可以由几个部件组成。
- 一道更难的美术测试，把不同来源的素材放在一起。
