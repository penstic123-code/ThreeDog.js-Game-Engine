# Logic review of the 0.8 work, 2026-11-05

Scope: `git diff 07db1dc7..HEAD -- packages`, read for faults that tests would miss. No engine or tool code was changed.

How each finding was checked:

- **Run**: reproduced with a small script.
- **Read**: followed through the code, not run.
- **Unconfirmed**: looks wrong from the code, but needs a real GPU or a page to prove.

Totals: 2 high, 7 medium, 13 low, 5 duplicates.

Severity means: high is wrong results or lost work in ordinary use; medium is wrong results in a narrower case, or a tool that reports something false; low is a rare case or a small effect.

## High

### H1. A second tune write can have no effect: the old value wins

`packages/tools/tune.mjs:63` and `:37`. Sure: **Run**.

`parseTuneBlock` puts any line it cannot read into `kept`, and `tuneBlock` writes `kept` after the new values. If a kept line sets the same path, it runs later, so the old value overrides the new one.

Two ordinary ways to get there:

- `main.js` has Windows line endings. Every line of the block ends in `\r`, the regexes end in `$`, and so every old line is kept.
- The author added a comment to a line of the block.

Result of the run, with exposure 1.2 in the block and 1.5 from the panel:

```
engine.renderer.toneMappingExposure = 1.5;
engine.renderer.toneMappingExposure = 1.2;   // keep it soft
```

The game keeps running at 1.2 and the tool says "Written". With line endings the old lines also stay on every later write.

Fix direction: split on `\r?\n`, and drop a kept line whose left side is a path the new values set.

### H2. The editor's undo history breaks when two steps overlap

`packages/tools/editor/design.js:181-193` (`act`) and `:290-298` (`walk`). Sure: **Run** (design.js with a stub page and a held server reply).

`act` and `walk` undo their own work by position: `done.pop()` and `from.push(to.pop())`. They assume nothing else touched the lists while they waited for the server. Nothing in `design.js` or `editor/index.js` stops a second step from starting during that wait, and holding Ctrl+Z repeats the key.

Failing case from the run: save scale 2 (accepted). Save scale 3, press Ctrl+Z before the reply, and the file has been edited by hand so both are refused.

- Expected history: `done [2]`, `undone []`.
- Actual history: `done [3]`, `undone []`.

The good save can no longer be undone, and the history holds a change the file never took. The next undo tries to take back something that never happened. `act` also replaces `history.undone` with its saved copy, so the two functions end up holding different arrays.

Two overlapping undos go wrong the same way when the first is refused and the second is not: the wrong step moves back.

Fix direction: one queue in `design.js`, so a step starts only when the last one has finished. That also fixes M2.

## Medium

### M1. A file put back to the editor's last text leaves the page on old values

`packages/tools/vite/vite-threedog-editor.js:45-51`. Sure: **Read**.

`written` keeps the last text the editor wrote and is never cleared, even when a different text is seen. Failing case:

1. The editor saves, so the file holds text T1.
2. The AI or a hand edit makes it T2. The page reloads and shows T2.
3. `git checkout` or Ctrl+Z in the code editor puts T1 back.
4. The text equals `written`, the hook returns `[]`, and the page stays on T2.

The header says "the page must never go on with old values". Fix direction: delete the entry when the text differs.

### M2. A drag or an edit made while a save runs is dropped without a message

`packages/tools/editor/design.js:201-209`, `packages/tools/editor/index.js:81-93`. Sure: **Read**.

`change` does not wait for the previous change, and the held `entry` still has the old file values.

- Second drag: its `expect` is the old value, so the server refuses it as a conflict. `stay()` then moves the model to the old position. By then the first save has landed and replaced `entry`, so `landed` sees `was !== entry` and shows nothing. The model stands at the old place, the handles at the new one, the file says the new one.
- Tabbing through two property rows: both writes succeed, but the second reply is dropped, so the panel holds a stale value for that row. The next edit of that row is refused as a conflict.

### M3. A lost WebGPU device reads as spare capacity in `threedog stress`

`packages/tools/stress-page.js:54`. Sure: **Unconfirmed** (read only; needs a real GPU pushed past its limit).

`error` only looks at `gl?.isContextLost`, and `gl` is null on WebGPU. The engine does learn of the loss (`core/page.js:73`), but `measure` never asks. After a loss, or after a buffer too large to create, draws stop costing anything. Frame times fall, the ramp carries on to the cap, and the table says "not crossed". That is the opposite of the truth, and the numbers go into a budget. Read `engine.page` in `measure`, and listen for uncaptured GPU errors.

### M4. Stress leaks every instanced mesh between steps

`packages/tools/stress-page.js:14`. Sure: **Read**.

`fresh()` frees geometries but never calls `InstancedMesh.dispose()`, so each step's instance buffer stays. The steps double, so by step n about twice the current load is held. At the top of the `instances` axis (12.8M instances, 64 bytes each, about 820 MB in the last step) the axis can stop on memory left over from earlier steps, not on the load it names. The bias is against the number the tool exists to report.

### M5. A refused value in the URL is never reported

`packages/engine/core/UrlState.js:171`, `packages/tools/capture.mjs` (the `--weather` line). Sure: **Read**.

`late()` runs the same `_ask` path, so `?weather=typo` fills `_refused`, but nothing reads it. `apply()` is the only place that returns it. `threedog capture --weather rian` prints a normal report of a frame in the game's default weather. That is the case this change was written to stop ("must not read as done"). The URL route needs a public way to read the list, and the tools that build a URL need to fail on it.

### M6. Any op with an internal NaN position now fails quietly

`packages/engine/core/opsRun.js:70`. Sure: **Read**.

The comment says this catch is for "a bad value that came in as an argument". It catches every `bad-position` thrown anywhere inside any op, including a game's own op that divides by zero. That used to reach `reportError` and stop the game where the bug was. Now the op returns `{ ok: false, code: 'badPosition' }` and nothing is reported. A caller that ignores the result never hears of it. `thing.set` already checks its argument in `can` (`goodPos`), so the catch is not needed for the case it was written for. See also D3.

### M7. Walking NPCs fill the new "Changed" line

`packages/engine/modules/world/persist.js:88-109`, `packages/tools/describe-snapshot.mjs:20`. Sure: **Read** (two branches meeting).

`worldChanges` strips `motion` but keeps `position` and every other field, so each walking NPC is a new row on every step. `world` is not in `MOVES_ALONE`, and the one-line answer keeps only four lines. In a town with a few walkers, the thing a `press` actually did can drop off the line. This is the failure `MOVES_ALONE` exists to prevent.

Two smaller effects, both unconfirmed:

- `worldChanges` compares every record on every describe, which may cost time in a large world.
- Runtime rows hold the live `rec.position` object, so a describe result kept in the page changes after it was taken.

## Checked, no fault found

- **Capture's private hook**: three sets `_handleObjectFunction = this._renderObjectDirect` at the start of every render (`Renderer.js:2077`), so the wrapper is picked up, and a rename fails loudly in the tool's refusal.
- **Light bake**: `atlas.meshes` keeps the order and count of `meshes`, so the index lines up. In three-mesh-bvh a `maxDist` of 0 means unbounded. The early returns skip `dispose`, but the page closes straight after.
- **Editor place maths**: the inverse in `poseFields` matches `content.where`.
- **Write order on the server**: `inOrder` does serialize the dev server's writes, and `handleHotUpdate` waits for them. A CLI write from another process has no lock; the unsafe window is synchronous and very short.
- **`world.forget`**: `_pending` is used up by the first insert, and `removeRecord` already clears the view, cells, simulation and `_unsaved`, so nothing else needs forgetting.
- **Stress draw counts**: the engine sets `info.autoReset = false`, so they cover every pass of a frame.
- **`_pressRefused`**: `pressedRaw` reads the fixed-step snapshot, so a press is logged once, and `ops.refused` only writes the log.
- **`applyState` result**: `ops.allow` returns what its function returns; every engine module with an `applyState` hook has `stateKeys`.
