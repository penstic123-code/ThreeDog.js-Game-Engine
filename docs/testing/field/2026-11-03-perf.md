命令：`npx threedog perf --only=pages --gpu 60`（真显卡）和 `npx threedog perf --only=pages --software 30`（软件渲染）。

## 这次发现并修掉的

- **无头浏览器的 WebGPU 一直没真跑过。** 之前所有"WebGPU"数字和截图都来自 WebGL2 后端，原因有两层：
  1. 笔记本双显卡时无头 Chromium 默认用集显；加 `--force_high_performance_gpu` 后用独显（游戏要的 `powerPreference: 'high-performance'` 就是它）。
  2. Playwright 带的 Chromium 没有 `dxil.dll`，D3D12 上 WebGPU 的 `requestDevice()` 报 "dxil.dll Windows Error 87"，引擎按设置悄悄退回 WebGL2 后端。
     加 `--disable-dawn-features=use_dxc` 让 Dawn 用 Windows 自带的 FXC 编译着色器，就能拿到真 WebGPU 设备。
  两个参数都加在 `packages/tools/browser.mjs` 的显卡启动参数里，shot / gallery / perf / stress 都受益。
- `perf` 新增 `pages` 一节和 `--renderer=webgl|webgpu|both`；拿不到 WebGPU 时那一行下面写出退回原因。

## 后来查清并修掉的：开放世界 WebGL 263 次绘制、WebGPU 198 次

原来记的"WebGL 263、WebGPU 198，软件渲染两边都是 198"不是档位问题。两条路线各跑 `engine.describe()`：档位都是 high，阴影设置一样
（pcf、2048、1 级、每帧更新），后期一样（bloom + MSAA）。差别有两层：

1. **WebGPU 上开放世界几秒后就冻住了。** 近处小植被（只长在玩家附近、按距离淡出的那类）的淡出着色补丁只有 GLSL 版，没有 TSL 版。
   开始后第一块带这种植被的地块一加进场景，WebGPU 路线就报"补丁只有 GLSL"、游戏冻结：画面停在那一帧，镜头、天气、植被都不再动。
   198 次就是冻住那一帧的数。修法：淡出补丁加上 TSL 版（`modules/vegetation/nearFade.js`）。同类问题还有一处：地形按纹理着色
   （`terrain({ shading: 'texture' })`）的颜色图补丁也只有 GLSL 版，一起补了（`modules/terrain/terrainTexture.js`）。
   守护测试：`engine content on WebGPU`（测试页里加了近处小草和一块纹理着色的地形，两条路线逐像素比，并检查没有冻结报错）。
2. **测量时镜头还在飞。** 开放世界启动后有 5 秒开场镜头绕小屋飞，绘制次数跟着视角在 210–270 之间变；`perf` 说"站着不动"，
   其实三轮采样有的落在飞行中、有的落在飞完后，取中间值时恰好挑到哪一轮就是哪个数。构建出来的页面不读 `?cutscene=skip`，
   所以 `perf` 的 pages 一节现在先等镜头连续 30 帧不动（最多 20 秒）再采样。

修完后真显卡重跑（`node packages/tools/perf.mjs --only=pages --gpu 60`）：

## 不开后期时用画布自带的抗锯齿（高档设备）

原来高档设备默认开抗锯齿，引擎自己的渲染器却总是不带画布抗锯齿建出来，抗锯齿只放在后期链的渲染目标里。于是一个效果都没开的游戏，
每帧也要先画进两张 4 倍采样的半浮点渲染目标，再整屏画一遍输出。现在引擎建渲染器之前先看一眼显卡定档位（临时建一个 1x1 的 WebGL
上下文读显卡名，一个页面只读一次），开局的抗锯齿就是画布自带的：没开效果时直接画到画布上。开了效果，或者运行中把抗锯齿切成另一个值
（画布的抗锯齿建好就改不了），才走后期链，抗锯齿在渲染目标里，和原来一样。游戏自己传进来的渲染器，抗锯齿默认跟它自己的设置走。

测法：小城测试页，关掉页面自带的泛光（这时一个效果都没有），无头浏览器窗口设成 2560x1440，关掉垂直同步（`--disable-gpu-vsync
--disable-frame-rate-limit`），每种情况采 600 帧取中间值，跑三次。显卡时间用的是引擎自己的计时查询（`EXT_disjoint_timer_query_webgl2`，
只有 WebGL 有）。修改前的数字是把改过的几个文件临时换回 65686791，在同一台机器上测的。测量脚本是临时的，没有提交。
`node packages/tools/perf.mjs --only=pages --gpu 60` 测的两页都带泛光，帧间隔又被刷新率卡在 16.7 ms，看不出这处改动（数字附在最后）。

WebGL，RTX 5060 笔记本，2560x1440，显卡 ms/帧（三次的范围）：

| 情况 | 修改前 | 修改后 |
|---|---|---|
| 没开效果，抗锯齿开（高档默认） | 0.93–1.01（走后期链，4 倍采样渲染目标） | 0.58（直接画到带抗锯齿的画布） |
| 没开效果，运行中关掉抗锯齿 | 0.53（直接画） | 0.55–0.56（走后期链，0 采样） |
| 开着泛光，抗锯齿开 | 1.47–1.49 | 1.62–1.64 |

- 高档设备上没开效果的游戏：显卡时间少约 40%，也省下两张 4 倍采样半浮点渲染目标的显存。
- 代价：开着效果时，最后那一遍输出画进的是带抗锯齿的画布，WebGL 上每帧多约 0.15 ms（约 10%）。画布的抗锯齿在建上下文时就定了，
  而开局时还不知道游戏会不会加效果（游戏的 plugins 和 look.post.add 都在后面），所以两头没法都省。
- 设置菜单"低"档关掉抗锯齿：在带抗锯齿的画布上改走 0 采样的后期链，显卡时间和原来直接画差不多（0.55 对 0.53）。
- WebGPU：渲染器建出来时就带 4 倍采样（`renderer.samples`），没开效果时直接画。WebGPU 拿不到逐帧显卡时间；关掉垂直同步后的帧间隔
  都在 3–5 ms 之间，主要是 CPU 时间，噪声比差别大，没有可信的前后对比。开着效果时画布本身不做多重采样（最后一遍是全屏四边形，
  three 在这里用 0 采样），所以没有 WebGL 那 0.15 ms 的代价。

## 首帧时间：从打开页面到玩家看到第一帧画面

**"首帧"怎么算。** 从浏览器开始打开页面（`performance.now()` 的零点，也就是导航开始）算起，到加载画面撤掉之后、主循环画完第一帧
（这一帧的绘制命令交给显卡）为止。引擎现在每次启动都记下这个数和它的八段，开发版和发布版都记，只是几次取时间，几乎没有开销：
`engine.startup.firstFrameMs` 和 `engine.startup.phases`，`describe().startup` 里有，`engine.inspect.perf().text` 多一行
`first frame: ... = script + construct + ...`，调试面板的启动一行也带上。八段加起来正好等于首帧时间：

| 段 | 意思 |
|---|---|
| script | 打开页面到 `createEngine` 开始：下载 HTML 和脚本、解析、执行游戏 main.js 顶上的代码 |
| construct | `createEngine` 本身（建渲染器、各项服务、加载画面） |
| setup | `createEngine` 之后到 `start()`：游戏装模块、摆场景 |
| init | `start()` 里读存档、初始化渲染器（WebGPU 要等适配器）、各模块 init |
| preload | 预加载资源 |
| world | 场景参数、等附近的地块等必须先建好的东西 |
| compile | 编着色器（compileAsync），再加一帧藏在加载画面后面的预热帧 |
| draw | 准备好到第一帧画完：engine:ready 的监听、标题页，再加等到下一次 requestAnimationFrame |

**命令。** `npx threedog perf --only=startup --gpu`（真显卡）和 `--software`（软件渲染）。都是构建版（vite build + preview），
每页每次开一个新浏览器（缓存全空），三次取中间值。空白模板是临时用 `new-game` 的模板生成到 `games/` 里构建，测完删掉。
开发版（npm run dev）这次没测：时间不够；开发版按需转译模块，数字只会更大，也不是玩家看到的。

**看出来的。**

- 每个有内容的页面，最大的一段都是 compile（占 40–60%）。真显卡反而比软件渲染慢：Windows 上 WebGL 经 ANGLE 转成 D3D11，
  着色器要过一遍系统的编译器，一个程序几十到两百毫秒；软件渲染编得快、画得慢。
- 空白模板 0.3 秒就出第一帧：引擎自己的固定开销（脚本、建引擎、一个程序）很小，时间都花在内容上。
- 软件渲染下 construct 多出约 130 ms：在 SwiftShader 上建 WebGL 上下文慢（含开局读显卡定档位的那个 1x1 上下文）。
- init 里最慢的是物理（120–150 ms，等 4 MB 的 Rapier 脚本和 WASM）；羊岛的 world 段 200–250 ms 是附近地形块。

**拆开 compile 看到的浪费**（临时探针脚本给 `renderer.render` / `compileAsync` 计时，没提交；真显卡、构建版）：

1. **房间环境图（PMREM）占了小城首帧的三分之一多。** 场景里有会读 `scene.environment` 的材质时，引擎在编着色器之前用 three 的
   `PMREMGenerator.fromScene(RoomEnvironment)` 生成基线环境图：4 次渲染、新编 6 个程序里的 4 个，真显卡上共约 410 ms
   （125 + 27 + 213 + 46，最慢的是模糊着色器），全是同步编译。小城 compile 段 575–690 ms 里，真正的 compileAsync 只有约 100 ms。
   开放世界同样约 410 ms。已改成和场景一起并行编译，见下面「首帧：砍掉三处浪费之后」。
2. **后期效果的程序在预热帧里一个一个同步编。** 开放世界预热帧之后，还有 9 次渲染各新编 1 个程序（每次约 14 ms，共约 130 ms），
   来自泛光等后期效果的各个全屏通道，compileAsync 看不到这些材质。已改成一起并行编译（WebGL），见下面。
3. **draw 段约 170 ms（开放世界、小城），羊岛、空白模板只有 3–17 ms。** 当时猜是在等显卡进程链接着色器；再查发现不是，
   是第一个物理步里 Rapier 第一次跑要编译 WASM（约 120 ms），见下面。
4. 首帧之前不需要的资源：首帧之前下载的只有脚本（引擎 1 MB、three 0.7 MB、Rapier 4.2 MB）和内容索引，寻路的 worker 在首帧之后
   才开始。没看到首帧之前多下载的模型或纹理。

## 首帧：砍掉三处浪费之后

改了什么（只动 WebGL 的编译路线，WebGPU 的环境图和后期照旧）：

1. **房间环境图**：开局先把环境图的生成"空跑"一遍，期间每次 `renderer.render` 都换成 `compileAsync`（`render/backend.js` 的
   `compileThrough`），于是它的 4 个程序和场景的程序一起交给浏览器并行编译；空跑留下一张尺寸对的空环境图先挂上，场景按它编；
   等程序都好了再真画一遍、换上真图。这些都在藏起来的预热帧之前，所以没有哪一帧缺环境图，也没有渐变。
2. **后期链**：同样空跑一遍后期链（`post.render(0)`），泛光等全屏通道的程序也进并行编译，不再在预热帧里一个一个编。
   WebGPU 不做：它的后期通道是一条管线里的节点，里面的渲染只在真的一帧里才跑；它的 `compileAsync` 也不能同时跑好几个。
3. **draw 段那约 170 ms 不是显卡在链接着色器**。再用探针看：准备好之后下一次 requestAnimationFrame 马上就来了（约 2 ms），
   时间花在第一个固定步里的物理 `world.step()`：77 个碰撞体也要约 120 ms，第二步就是 0 ms。原因是浏览器第一次调用 WASM 函数时才编译它，
   第一步把 Rapier 整条步进路径都编了一遍。改法：物理模块在一个用完就扔的小世界里先走几步（加上角色控制器），放在开局等显卡编译的
   空档里跑（模块上下文新加 `ctx.whileCompiling(fn)`）；游戏自己的物理世界不动，不走游戏时间。第一次试用 setTimeout，
   结果落进了 WebGPU 等附近地块的时间里，那一段多了约 150 ms，所以改成明确放在编译空档里。
   顺带：`perf` 生成空白模板时建了 `games/` 又留下一个空文件夹，现在是它建的、又空了就删掉。

draw 54），开放世界 WebGPU 1505（1432），小城 795（681；compile 259），羊岛 1297（905，三次里差很多：932 / 1297 / 1413），
WebGPU TSL 788（678）。软件渲染上并行编译几乎不省什么（编译本来就快，空跑多了一遍准备工作），物理预热只是从 draw 挪到 compile，
所以看不出变快，小城的 compile 还多了约 90 ms。首帧报警（软件渲染）这次比值 81.61，基线 76.55，在 1.5 倍以内；没变快，基线没改。

## 首帧变慢的报警

`tests/perf-baseline.json` 多了 `firstFrame.software` 一条；测试 `PERF first frame slowdown alarm` 和原来的帧耗时报警放在一起
（`tests/specs/perf-alarm.mjs`），单独跑（serial），软件渲染。做法：开放世界页先开一次（热一下着色器缓存），然后把这页换成空白页，
再开 5 个新标签页（每个缓存都是空的，像第一次访问）各测一次首帧，取最快的一次；每开一个标签页之前，在空白页上跑同一段固定的
JS 计时（校准），首帧除以校准的中间值再和基线比，超过 1.5 倍算红。

为什么这么做：一开始用刷新页面，刷新的计时从旧页面卸载之前就开始了，卸载开放世界在软件渲染上要 2.5 秒，全算进了 script；
接着改成新标签页，但原来那页还在跑开放世界，旁边标签页的首帧慢了 7 倍；校准放在游戏页里跑，会和游戏自己的循环抢 CPU，忽大忽小。
取最快的一次，是因为机器忙只会让它变慢、不会变快，中间值在两次安静的运行之间也差了 35%。

基线：首帧 1133 ms，校准 15 ms，比值 76.55（2026-11-03）。之后两次运行（机器上同时有别的活）：94.12、95.07，约 1.23 倍，
在 1.5 倍以内。校准抵消不了显卡进程那边的负载（启动有一大块在显卡进程里编着色器），所以门槛比帧耗时报警（1.3 倍）松。
它要抓的是"开局把所有着色器都编一遍""第一眼之前加载了整关"这种翻倍的变化。有意改动之后重写基线：
`npm test -- "first frame" --update-snapshots`。
