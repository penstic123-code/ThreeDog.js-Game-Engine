# 2026-11-05 很多灯：真灯数量、lightPool、阴影、运行中加灯

分支 `test/many-lights`。只加了测试方法（`packages/engine/tests/stress-field/lights.js`，由 `main.js` 挂进 `window.sf`）和一条开发警告（见末尾）。
复现：`node packages/engine/tests/stress-field/run.mjs lightsReal '{"n":64}'`；其余方法 `lightsPool`、`lightsChurn`、`lightsPoolEdge`，参数见表。

## 机器和负载

Windows 11，NVIDIA RTX 5060 Laptop（Chrome 适配器 nvidia/blackwell，fallback=false，真 GPU），系统 Chrome 无头，1280x720，像素比 1，WebGPU（`renderer: 'webgpu'`），手动跑帧不限 vsync。机器上还有别的助手，噪声约 10-30%。
场景：`lights: false`（游戏自己写光），一个很弱的半球光，MeshStandardMaterial 地面 + 300 个箱子（引擎合批后约 94 次绘制），镜头从高处俯看，所有灯都在画面里。点光 intensity 60、distance 18。
**灯确实进了画面**：每项都把画布读回量平均亮度（0-255）：无灯 31.96，n=1 33.5，n=8 42.1，n=32 70.7，n=128 121.0，灯数一增亮度就涨；把灯强度设 0 又回到 31.96。上一次的数作废是因为灯被藏起来，这次用亮度读数证明灯有效。

## 1. 真点光数量（无阴影）

CPU ms 每帧（吞吐 ms：排队 40 帧再等 GPU 排空）。

| 灯数 | CPU ms | 吞吐 ms | 最坏帧 | start() 编译 ms |
|---|---|---|---|---|
| 1 | 1.5 | 1.5 | 4.1 | 461 |
| 8 | 2.1 | 2.2 | 3.7 | 550 |
| 16 | 1.8 | 1.9 | 2.6 | 619 |
| 32 | 1.7 | 1.8 | 5.0 | 811 |
| 64 | 1.8 | 1.9 | 3.7 | 1338 |
| 128 | 2.2 | 2.7 | 3.3 | 2373 |

- 这台 GPU 上 128 盏无阴影点光仍是 2.7 ms：每帧成本几乎不随灯数涨。灯数的代价在**启动编译**（128 盏 2.4 s，每多一盏约 15 ms）。这是一块强显卡、简单场景的结果，手机和集显的墙在更低处（引擎的 `many-lights` 警告线定在 8 盏），这里量不到。

## 2. lightPool（固定池，源很多）

池 8 盏真灯，无阴影：16 个源 1.7 ms，100 个源 2.5 ms，400 个源 2.5 ms（吞吐）。源数从 16 到 400，帧时间基本不变（选灯每 0.1 s 一次，成本低）。池 4 / 8 / 16（100 源）：2.5 / 2.5 / 2.3 ms，亮度 33.2 / 37.2 / 46.7，池大了画面亮但不更慢。

## 4. 运行中加灯 / 减灯 / 显隐（卡顿）

基础 8 盏，对已经运行的场景改一次，量改完那一帧（含 GPU 排空）：

| 操作 | 稳态 ms | 改完第一帧 ms |
|---|---|---|
| scene.add 一盏 | 5.5 | **374** |
| scene.remove 一盏 | 5.3 | **345** |
| visible = true | 6.0 | **263** |
| 只改 intensity 0 -> 60（池的做法） | 6.2 | **7** |
| 基础 32 盏，加一盏 | 6.6 | **1086** |

加减灯时 three.js 为每种材质重新编译着色器，卡 0.25-1.1 s，基础灯越多越久；第二帧起恢复。改 intensity 不卡。已有的 `light-recompile` 警告说的就是这个，数字现在有了。

## 5. lightPool 边缘和切换会不会闪

12 盏灯排成一行，池 4 盏，镜头沿线走 24 s（1440 帧），每帧读每个槽的强度和位置：
- 槽换源共 3 次/槽。换的瞬间光已淡到 <= 一帧的步长（最大每帧强度变化 3.33，满强度 60，即 5.5%），然后才移动位置，**没有看得见的跳变**。
- 稳定后同时亮的灯数 3-4：换源时池先把旧源淡出（0.3 s）再让新源淡入，所以新进入范围的灯最多晚约半秒才亮，期间亮的灯比池少一盏。这是设计里的"先淡出再接新源"，不是 bug；要更跟手可以调小 `fade`，代价是换得更生硬。
- 池边缘：池外的源就是暗的（100 个源、池 8 个，亮度只比池 4 个高一点），池大小决定"能看到几盏灯"；镜头走近时边缘源要等淡出淡入完才亮。

## 结论和要协调者定的

- 没有找到需要在引擎里修的 bug：数量、阴影、加灯卡顿都是 three.js 的代价，引擎已有 `many-lights` / `light-recompile` 警告和池。
- 要定：池换源的 0.3 s 先淡出再淡入，是否改成"新旧交叉淡"（边缘灯早亮，但短暂要多一盏真灯预算）。我没改。
- 没测：手机 / 集显、聚光灯、阴影分辨率 1024 以上、有后期时的影响、WebGL 后端对照。每项只跑一次，未重复。

## 开发警告（同批新增）

游戏自己加了灯，而引擎默认的占位灯（`engine.lights.sun`、`engine.lights.hemi`）还亮着，两者会叠加，画面比游戏想的亮。现在开发模式第一次遇到会在控制台提示一次，文字里点名修法：`createEngine({ lights: false })`。`lights: false`、占位灯已移出场景或熄灭、引擎模块自己的灯、灯池的灯都不提示。只是提示，不拒绝，不改灯（three.js 的灯本来就是相加）。实现在 `packages/engine/core/gameLights.js`，规格在 `tests/specs/lights.mjs`。原来只有 `createEngine` 开头一条"占位画面开着"的提示和 `many-lights` / `light-recompile`，没有这一条。
