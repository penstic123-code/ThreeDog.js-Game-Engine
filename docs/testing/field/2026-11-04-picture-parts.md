# 2026-11-04 画面件实测：无上下文助手能不能靠报错改好一次冲突

**题目。** 一个新小游戏《Harbor Night》，三个不同写法的画面件：天空（类，占 `sky`、`sun`）、海（普通对象，`frame` 钩子，占 `fog`）、雨（闭包工厂，没占位）。埋一处冲突：雨每帧写 `scene.fog.far`（"大雨压低视距"），而雾归海。这题有一个陷阱：照报错第一条直接删掉，警告没了，大雨压低视距的效果也没了。

**给助手的东西。** 游戏文件夹、`check.mjs` 的输出（`picture-held` 警告全文）和一句"Fix this"，外加汇报要求。一个新开的通用助手，没有这次任务的上下文。

**结果。**

| 项 | 结果 |
|---|---|
| 冲突改好了吗 | 改好了。我重跑 `check.mjs`：警告没了，`fog.far` 71.3（海的 178.24 乘雨的 0.4，两边都上了屏幕；之前 80 是雨盖掉海） |
| 选的修法 | 第 3 条：共享值。海定义 `fog.reach` 并且是 `fog.far` 唯一写的人，雨用 `ctx.mod` 改它，还加了 `requires: ['fog']`。没掉进"直接删"的陷阱 |
| 试了几次 | `check.mjs` 跑了 1 次，一次过 |
| 不看文档能改好吗 | **不能。** 它读了菜谱 62、55 全文，`core/stacks.js` 全文，`core/modules.js` 一段，并搜了 `core/` 和 `modules/`。按"不看文档"这条标准，这次不算通过 |
| 卡在哪 | 报错和菜谱都只写了固定的 `ctx.mod(name, { mul: 0.5 })`，而雨的量每帧在变。`handle.change(v)` 两份菜谱都没提，它是在 `core/sharedPoint.js` 的注释里找到的 |
| 小问题 | 报错写 `ctx.mod`，菜谱 62 的共享值一节写 `engine.mod`，它要去菜谱 55 才弄清区别 |

**改了什么（只改一次）。** 报错的第 3 条加上 `const h = ctx.mod(name, { mul: 1 })` 和每帧 `h.change(x)`；菜谱 62 的共享值一节写上同样的话，并说明模块里用 `ctx.mod`。改完没有再找新助手验证，所以"这句话够不够让助手不读源码"还不知道。

**顺带发现（没改）。** 这个游戏里 `uTimeOfDay` 不动：它只由引擎的 `sky()` 写，用自己天空的游戏拿不到；菜谱 62 的信号表写的来源是 sky，表没错，但自己写天空的件容易踩到。助手还留了一帧延迟：雨在 `onRender` 改值，海在更早的 `frame` 读，平滑变化时看不出来。

**局限。** 只跑了一次、一个助手、一种冲突。这个助手也能看到仓库里的文档和源码，真实游戏项目里它看到的是发行包。
